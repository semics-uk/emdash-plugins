## Notes

**Budget.** Counted honestly, the route needs more than the 10 calls the criteria list: settings
(Turnstile secret, hold settings) 1, reads 3, rate limit 2 (shared `rateLimit` is get + set),
Turnstile 1, draft write 1, `reserve` N, draft → held 1. So an occurrence order (N ≥ 3) could not fit.
Three changes make it fit:

1. **Denormalised reads.** `config/save` now writes a `catalog` on the event config: each ticket
   type's capacity, price, hidden flag, per-order limits and sales window, and each occurrence's
   capacity, start and status. It has no counters. Checkout reads only the config. A stale capacity
   is safe because every reservation guard pins the capacity it planned with, so a mismatch fails as
   sold out. `config/save` rewrites the catalog to match the documents as they end up on every exit,
   including partly failed saves. The write costs one call, and only when the catalog changes.
   `config/get` leaves the catalog out of its response. `counterlessChanges` skips `catalog`.
2. **Rate limit in one call, not KV.** The limit counts this IP's bookings from the last 10 minutes
   (`bookings.count({ ipHash, createdAt ≥ … })`, new index `["ipHash","createdAt"]`), so the booking
   write is the increment. The limit is 10 bookings per IP per 10 minutes. The IP hash uses shared
   `hashIp`, salted with the Turnstile secret (or the plugin id if no secret is set). This departs
   from "a rate-limit KV call". Requests that fail Turnstile or are sold out at the pre-check are
   not counted. Turnstile covers those.
3. **Bounded compensation.** `planReservation({ compensation: "bounded" })` bounds only the forward
   steps. `reserve(…, { maxCalls })` compensates as far as the budget allows, earliest steps first,
   and returns the rest as `uncompensated`. The route then sets the draft's `holdExpiresAt` to now.
   The sweeper closes the draft after the draft grace period and marks the event dirty for drift
   repair. A fully compensated miss moves the draft straight to `expired`.

Calls with Turnstile configured: one ticket type, no occurrence: 8. Occurrence plus two ticket types:
10. Every path is asserted ≤ 10, and the common path ≤ 8. If no Turnstile secret is set, Turnstile is
skipped (one call fewer).

**Idempotency.** `idempotencyKey` is required: at least 32 URL-safe characters, generated by the
client for each checkout attempt. The booking id is `bk_` + SHA-256(key), and the 10-character
Crockford `ref` comes from the same digest. The draft is created with `compareAndSet(id, null, …)`.
A resubmit gets the same booking and a reissued access token. Only the hash is stored, so the first
token cannot be returned again, and the first response may never have arrived. If the booking is
held, the reissue goes through `extendHold(…, stepTarget(…), { accessTokenHash })`. A confirmed
booking keeps its emailed token and gets no new one. A lapsed hold returns `HOLD_EXPIRED`. Reusing a
key for a different order returns `BAD_REQUEST` (`IDEMPOTENCY_KEY_REUSED`). A double submit
re-sends a Turnstile token Cloudflare has already spent, and an order that is now sold out because
the first submit took the seats would also be refused. In both cases the route looks the booking up
by the key (one read) before refusing.

**Hold guards.** Draft → held, draft → expired, the draft re-token and the held re-token all guard
on the status read and `releaseClaimedAt: null`. A miss on draft → held returns `HOLD_EXPIRED`. The
seats are not released, because the expirer's close plus drift repair settle them. The `hold-<ref>`
accelerator (`scheduleHoldTask`) is scheduled only when the invocation stays within the 8-call
target. With Turnstile configured it is skipped, so **T048 `checkout/continue` should schedule or
re-arm it** at its first step.

**Other.** Inputs are validated with `zod/mini` (strict objects, email normalised to lower case).
It is a new devDependency, inlined into the bundle. The bundle grows from 23 KB to 56 KB; full
`zod` would be 118 KB. Adding it re-resolved some peer entries in `pnpm-lock.yaml` offline. Errors
are returned as `{ ok: false, error }` bodies, like the other routes. BUILD-PLAN §3.1's bookings
index list does not yet show `["ipHash","createdAt"]` or the config `catalog`.

## Notes

- **Additions to BUILD-PLAN §5** (design decisions made here; reviewers please confirm):
  - Intent gains `iat` (needed for "not yet valid" and to enforce the 30-min cap verifiably), plus
    optional `as` (`self`/`guardian`/`buyer`), `participant` (required iff guardian) and `delivery`
    (`inline`/`email`) so the §3.1/R5 waiver rules (buyer signs inline for self and minors, other
    adults by email) can be expressed. Lookup and catalog requests are `{v,typ,cid,ts[,ref]}`.
  - Receipts have no `exp` (durable evidence; replay is harmless because processing is idempotent and
    monotonic). `pdfSha256` may be `null` on a completed receipt while the PDF is still being
    generated; `pdfSha256`/`finalHash` are `null` for non-completed statuses.
  - `(cid, ref)` idempotency refined: an existing envelope is returned unless it is
    `declined`/`voided`/`expired`, in which case a new one is created (otherwise a signer could never
    retry after an expired email envelope).
- Error codes follow T012's naming (`TOKEN_EXPIRED`, `TOKEN_INVALID`, …). Wrong prefix, wrong secret,
  tampered payload and tampered signature all yield `TOKEN_INVALID` by design. The check order in §6.2
  is normative so multi-fault tokens give the same code everywhere; vectors pin it.
- 102 vectors: intent 53, receipt 19, lookup 11, catalog 10, pairing 9. Beyond the test file, all 102
  were cross-checked against a throwaway independent implementation of the spec (not committed;
  T012 builds the real one): 0 mismatches.
- `docs/protocol/biome.json` (nested, `extends: "//"`) excludes the generated `vectors.json` from
  Biome, because reformatting would break the byte-for-byte reproducibility check.
- `pnpm verify` passes but does not run `docs/protocol/vectors.test.mjs`; the root `test:scripts`
  glob covers only `scripts/*.test.mjs`. Left for the root-config owner.
- No changeset: no published package changed.

# Translations and right-to-left layouts

The Events and E-sign UI kits (the components, the injected pages and their client scripts) show no text of
their own: every word comes from a translation table in the package's `src/i18n/` folder. English (`en.ts`)
is the source language and Arabic (`ar.ts`) ships beside it as the first right-to-left language (T102,
EU-NFR-04, SU-NFR-06).

The sandboxed cores are not translated. They answer with codes (`SOLD_OUT`, `held`,
`SIGNING_TOKEN_EXPIRED`) and the UI turns each code into text, so the message tables never enter the
backend bundle (BUILD-PLAN §12 R51, R58). The emails, calendar files and admin pages that the cores render
are English for now.

## Choosing the language

A component's language is the first of:

1. its `locale` prop (`<BookingWidget event="…" locale="ar" />`);
2. `Astro.currentLocale`: the page's locale when the site configures
   [Astro i18n](https://docs.astro.build/en/guides/internationalization/). The injected pages (`/booking`,
   `/_events/check-in`, `/_events/sign`, `/sign/[token]`, `/signed/[token]`, `/verify`) and the Portable Text
   blocks use only this one;
3. British English (`en-GB`).

The locale also formats dates, times, numbers and prices (`Intl`). Its language subtag picks the table:
`ar-EG` uses `ar`, and a language without a table (`fr`) shows English, left to right.

A site that is wholly in one language can set Astro's `i18n: { defaultLocale: "ar", locales: ["ar"] }`; every
page, including the injected ones, then uses Arabic.

## Right to left

Every component sets `lang` and `dir` on its own root element, and the injected pages set them on `<html>`,
so a component reads correctly inside a page of any direction. Styles use logical properties
(`margin-inline-start`, `border-inline-start`, `inset-inline-start`) and never `left` or `right`, so the
layout mirrors by itself. `scripts/i18n-strings.test.mjs` fails on a physical side in a component's styles.

## Adding a language

1. Copy `packages/events/src/i18n/ar.ts` to `<lang>.ts` (the BCP 47 language subtag, such as `fr` or `he`) and
   translate every value. Keep each `{placeholder}` exactly as it is; you may move it within the sentence.
   The file is typed against English, so `tsc` lists any key you missed.
2. Plurals: a key ending in `.one` / `.other` (`booking.lines`) has plural forms. Add the forms your language
   needs from `Intl.PluralRules` (`zero`, `two`, `few`, `many`); a form may leave the number out (Arabic's
   "تذكرتان", two tickets). `other` is the fallback.
3. Register the table in `LANGUAGES` in `packages/events/src/i18n/index.ts`. A right-to-left language is
   already in the `RTL` set (Arabic, Hebrew, Persian, Urdu and others); add it there if not.
4. Do the same in `packages/esign/src/i18n/`. The two packages keep separate tables because neither may import
   the other or the private shared package (R35).
5. Run the package tests: `tests/ui/i18n.test.ts` checks that the new table has every key, no empty value and
   the same placeholders as English.

The consent wording on the signing page is the site's own setting (E-sign settings), so a site writes it in
its language there. Event titles, venues, ticket names, questions and document text are the site's content.

## Adding a string

Put the English text in `en.ts` under a key named for where it shows (`widget.…`, `booking.…`, `sign.…`), add
it to every other table, and use `t("key")` in the component. Text a client script shows travels in a
`data-messages` attribute that the component fills with `clientMessages(locale, "<prefix>.")`; the script
reads it and holds no text of its own. Put an element (a link, `<strong>`, `<time>`) inside a sentence with
`segments(t("key"))`, so each language decides where it goes. `scripts/i18n-strings.test.mjs` fails on text
written straight into a component, a UI helper or a client script.

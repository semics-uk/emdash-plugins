# voucher/1: the Vouchers ↔ Events redemption protocol

Status: **draft for 1.0** · Version: `voucher/1` · Requirements: R16 · Source: T163 (gift vouchers spec) §5, §6, §8.

Test vectors: [`voucher-vectors.json`](voucher-vectors.json), generated by
[`generate-voucher-vectors.mjs`](generate-voucher-vectors.mjs) and checked by
[`voucher-vectors.test.mjs`](voucher-vectors.test.mjs) (`node --test docs/protocol/voucher-vectors.test.mjs`).
Reference implementation: `packages/shared/src/voucher.ts` (tokens, pairing) and
`packages/shared/src/voucher-code.ts` (codes).

The key words MUST, MUST NOT, SHOULD, SHOULD NOT and MAY are used as in RFC 2119 / RFC 8174.

## 1. Purpose and roles

`semics-vouchers` sells gift vouchers; `semics-events` takes bookings. They are sandboxed EmDash plugins that
cannot share storage or call each other, so the site's Astro code (the suite) carries small HMAC-signed tokens
between them, in-process on the server.

| Role | Who | Issues | Verifies |
| --- | --- | --- | --- |
| **Voucher service** | `semics-vouchers` | hold tokens, lookup requests | settle tokens |
| **Client** | `semics-events` (Events Pro) | settle tokens | hold tokens, lookup requests |

Vouchers' admin creates a client: a `clientId` and a shared secret, shown once as the **pairing string**, which
staff paste into Events Pro's `vouchersPairing` setting. Both directions use the same secret; the per-type
prefixes (§4) give domain separation.

This protocol reuses the `esign-intent/1` primitives unchanged ([`esign-intent-v1.md`](esign-intent-v1.md)):
base64url (§2.1 there), text and JSON rules (§2.2 there), the token format and HMAC (§4 there) and the
verification algorithm (§6 there, steps 1–7). Only the prefixes, payloads and parameters differ. There is no
new cryptography.

## 2. Encoding primitives

As `esign-intent/1` §2: base64url without padding, decoded canonically (any character outside the URL-safe
alphabet, a length `≡ 1 (mod 4)` or non-zero unused bits is malformed); payloads are strict UTF-8 JSON objects
with no byte-order mark; the signature covers the received payload segment exactly, never a re-serialisation;
times are integer Unix seconds that are safe integers `≥ 0`.

Issuers SHOULD serialise with `JSON.stringify` and the field order of §5, so the vectors can be reproduced byte
for byte.

## 3. Pairing string

```
pairing  = "voucher1." clientId "." secret
clientId = 4*64( ALPHA / DIGIT / "-" / "_" )
secret   = 43( base64url character )    ; canonical encoding of exactly 32 bytes
```

- Regex: `^voucher1\.([A-Za-z0-9_-]{4,64})\.([A-Za-z0-9_-]{43})$`, plus canonical decoding. Anything else is
  `PAIRING_MALFORMED`.
- The secret is 32 bytes, the raw HMAC key. Vouchers MAY derive it from a master key (as e-sign does) or draw it
  from a CSPRNG; the client cannot tell.
- Vouchers SHOULD generate client ids as `cl_` and 16 random lowercase base32 characters, and never reuse one.
- Parsers MUST NOT trim; settings UIs SHOULD trim before saving. The pairing string is a secret: store it as a
  `secret` setting, never log it.
- The `voucher1.` prefix differs from `esign1.`, so an e-sign pairing pasted into the vouchers field is
  rejected instead of silently pairing the wrong plugin.

## 4. Token format

```
token      = payloadB64 "." signature
payloadB64 = base64url( UTF-8 JSON payload )                             ; non-empty
signature  = base64url( HMAC-SHA256( secret, prefix "." payloadB64 ) )   ; exactly 43 characters
```

| Token type | Prefix | Issuer → verifier | Max length (characters) |
| --- | --- | --- | --- |
| Hold | `voucher-hold/1` | Vouchers → Events | 1024 |
| Settle | `voucher-settle/1` | Events → Vouchers | 1024 |
| Lookup request | `voucher-lookup/1` | Vouchers → Events | 1024 |

A verifier always knows the type it expects from the route it serves and uses only that prefix, so a token of
one type never verifies as another (nor as an `esign-*/1` token, whose prefixes differ). The signature MUST be
compared in constant time.

## 5. Payloads

Every payload starts with:

| Field | Type | Rule |
| --- | --- | --- |
| `v` | integer | MUST be `1` |
| `typ` | string | `"hold"`, `"settle"` or `"lookup"`, matching the prefix |
| `cid` | string | `clientId` grammar (§3). Selects the key |

Grammars:

- `id64` = `^[A-Za-z0-9_-]{1,64}$`
- `ref` = `^[A-Za-z0-9._:-]{1,128}$`: the Events booking reference
- `currency` = `^[A-Z]{3}$` (ISO 4217, upper case)
- `minor` = an integer `0 ≤ n ≤ 10000000` in the currency's minor units (at most 100,000.00)

Unknown top-level fields and unknown fields inside `line` MUST be ignored (they are still signed).

### 5.1 Hold (`voucher-hold/1`)

Issued by Vouchers `public/redeem/hold` once it has taken the amount off the voucher. The suite hands it to
Events Pro on `public/checkout/continue`.

| Field | Req. | Type | Rule |
| --- | --- | --- | --- |
| `v`, `typ`, `cid` | yes | | `typ: "hold"` |
| `rid` | yes | string | `id64`: the redemption id, unique per hold |
| `iat` | yes | integer | Issue time |
| `exp` | yes | integer | `exp > iat` (else `PAYLOAD_INVALID`); `exp − iat ≤ 1800` (else `TOKEN_LIFETIME_EXCEEDED`) |
| `ref` | yes | string | `ref`: the booking the hold is for |
| `kind` | yes | string | `"money"` or `"activity"` |
| `amountMinor` | yes | integer | `minor`. Money: the amount held, `≥ 1`. Activity: the ticket's unit price as Vouchers was told it, `≥ 0` |
| `currency` | yes | string | `currency` |
| `line` | iff `kind = "activity"` | object | `{ eventId: id64, ticketTypeId: id64 }`: the ticket type the voucher pays for. MUST be absent for money |

Issuer rules (Vouchers): one fresh `rid` per hold; `exp` at most 30 minutes after `iat` (the checkout window).

Client rules (Events Pro), after verifying:

- `ref` MUST be the booking being continued, and `currency` the booking's currency; otherwise refuse the hold
  (`PAYLOAD_INVALID`) and continue without it.
- Money: discount `min(amountMinor, due)`. Activity: the booking MUST contain a ticket of `line.ticketTypeId` for
  `line.eventId`; discount `min(amountMinor, that ticket's price, due)` for one ticket.
- Idempotent on `rid`: the same hold twice changes nothing. A booking carries at most one redemption; a new
  `rid` replaces the old one, which is then reported as `released` (§8.3).
- A hold needs no nonce: replaying it can only re-apply the same `rid` to the same booking.

### 5.2 Settle (`voucher-settle/1`)

Issued by Events for a redemption, on the confirmed and booking pages, after a cancel or refund, and in answer to
a lookup (§8.3). The suite hands it to Vouchers `public/redeem/settle`.

| Field | Req. | Type | Rule |
| --- | --- | --- | --- |
| `v`, `typ`, `cid` | yes | | `typ: "settle"` |
| `rid` | yes | string | `id64`: the hold's `rid` |
| `ref` | yes | string | `ref`: the hold's `ref` |
| `outcome` | yes | string | `"confirmed"`, `"released"` or `"credited"` |
| `creditMinor` | yes | integer | `minor`. `≥ 1` when `outcome = "credited"`: the **total** credited back for this `rid` so far. MUST be `0` otherwise |
| `at` | yes | integer | When the booking reached the outcome |

- `confirmed`: the booking is confirmed with the voucher applied; the hold becomes spent.
- `released`: the booking will never use the hold (expired, declined, abandoned, or it carries another `rid`);
  the whole hold goes back to the voucher.
- `credited`: a confirmed booking was cancelled or refunded; `creditMinor` goes back to the voucher, capped at the
  amount held. For an activity voucher any `credited` makes the voucher usable again.

Settle tokens carry no `exp`: like e-sign receipts they are durable facts and may arrive days later. Vouchers
processes them idempotently and monotonically: `held → confirmed → credited` (a higher `creditMinor` credits the
difference) and `held → released`. A `released` is final. A `released` for a confirmed hold is ignored, and a
`confirmed` or `credited` for a released hold is recorded for staff, not applied.

Vouchers MUST NOT apply a `released` before the hold's `exp + 60` has passed (it keeps the hold and settles on a
later call): until then Events could still accept the hold token, so a release could let one balance pay twice.

Events SHOULD mint settle tokens deterministically from the stored booking (fixed field order, `at` from the
booking), so the same state always yields the same token.

### 5.3 Lookup request (`voucher-lookup/1`)

Issued by Vouchers when a code with an open hold is used again, so the suite can ask Events for the hold's outcome.

| Field | Req. | Type | Rule |
| --- | --- | --- | --- |
| `v`, `typ`, `cid` | yes | | `typ: "lookup"` |
| `ts` | yes | integer | Issue time |
| `ref` | yes | string | `ref`: the hold's booking |
| `rid` | yes | string | `id64`: the hold's `rid` |

Lookup requests are short-lived, read-only and idempotent, and travel in-process, so they carry no nonce.

## 6. Verification

### 6.1 Parameters

| Name | Value |
| --- | --- |
| Clock-skew allowance `S` | 60 s |
| Hold max lifetime | 1800 s (`exp − iat`) |
| Request max age `A` (lookup) | 300 s |

### 6.2 Algorithm

`esign-intent/1` §6.2 steps 1–7, with this protocol's prefixes, maximum lengths, schemas and parameters. The
first failure is the result:

1. **Size.** Longer than 1024 characters → `TOKEN_TOO_LARGE`, before any decoding.
2. **Structure.** Exactly two `.`-separated segments, the payload non-empty, both canonical base64url, the
   signature exactly 43 characters → else `TOKEN_MALFORMED`.
3. **Payload decoding.** Strict UTF-8 without BOM, JSON, a top-level object with a `cid` in the `clientId`
   grammar → else `TOKEN_MALFORMED`.
4. **Client.** `cid` unknown → `CLIENT_UNKNOWN`; revoked → `CLIENT_REVOKED`. Events' table has the one entry
   from its pairing string.
5. **Signature.** `HMAC-SHA256(secret, prefix(T) + "." + payloadB64)` compared in constant time → else
   `TOKEN_INVALID`. Wrong prefix, wrong secret and tampering are indistinguishable.
6. **Schema.** `v`, `typ` (MUST equal `T`) and the type's fields (§5) → `PAYLOAD_INVALID`. For holds,
   `exp − iat > 1800` → `TOKEN_LIFETIME_EXCEEDED` after the other schema checks.
7. **Time.** `iat` (hold), `at` (settle) or `ts` (lookup) greater than `now + S` → `TOKEN_NOT_YET_VALID`. A hold
   with `now > exp + S`, or a lookup with `now > ts + A + S` → `TOKEN_EXPIRED`. Settle tokens do not expire.

Boundaries are inclusive: `now = exp + 60` is valid, `now = exp + 61` is expired.

On success the result is the decoded payload: `{ ok: true, payload }`, else `{ ok: false, code }`.

## 7. Voucher codes

A code is the bearer credential for a voucher. It never travels in a token.

- **Generation.** 10 bytes (80 bits) from a CSPRNG, read as one big-endian 80-bit number and split into 16 groups
  of 5 bits, most significant first. Each group indexes the Crockford base32 alphabet
  `0123456789ABCDEFGHJKMNPQRSTVWXYZ`. Every symbol is equally likely in every position.
- **Display.** Four groups of four joined by `-`: `XXXX-XXXX-XXXX-XXXX`.
- **Normalisation** (what a person types → the canonical code):
  1. More than 64 characters → invalid.
  2. Remove spaces, tabs, carriage returns, line feeds and `-`.
  3. The rest MUST be exactly 16 ASCII letters or digits → else invalid. (Checked before case folding, so no
     non-ASCII character can fold into a valid one.)
  4. Upper-case it, then map `O → 0`, `I → 1`, `L → 1`.
  5. Every character MUST now be in the alphabet (so `U` is invalid) → else invalid.
- **Id.** The voucher's document id is the lowercase hex SHA-256 of the canonical code's ASCII bytes, so the
  database never holds a working code. Codes typed in any case, grouped or not, or with `O`/`I`/`L` for
  `0`/`1`, give the same id. Staff search by the code's last four characters, stored separately.

An invalid, unknown, expired or void code is answered with the one code `VOUCHER_INVALID` (§9).

## 8. Endpoints and behaviour

Tokens and codes travel only in JSON POST bodies passed in-process by the suite. They MUST NOT appear in query
strings, paths or logs, with one exception: the voucher page link `/_vouchers/v?c=<code>` in the voucher's own
email, which serves `Referrer-Policy: no-referrer`. Error bodies are
`{ "ok": false, "error": { "code": "VOUCHER_INVALID", "message": "…" } }`; as in `esign-intent/1` §9, a sandboxed
core answers them inside the host's `{ "success": true, "data": … }` wrapper with status 200, so callers branch on
`ok` and `error.code`.

### 8.1 `POST public/redeem/hold` (Vouchers)

Request `{ "code", "ref", "dueMinor", "currency", "lines": [ { "eventId", "ticketTypeId", "unitMinor", "qty" } ] }`.
The suite takes `ref`, `dueMinor`, `currency` and `lines` from Events' reserve reply, never from the browser. The
route is rate limited per IP.

Vouchers normalises the code (§7), checks status, expiry, kind and currency (`VOUCHER_CURRENCY`), and for an
activity voucher that `lines` has its ticket type (`VOUCHER_WRONG_ACTIVITY`). If the voucher has an open hold, it
first settles it through a lookup (§8.3). It then takes `min(balance, dueMinor)` (money) or the voucher itself
(activity) with one guarded write; nothing left → `VOUCHER_NO_BALANCE`.

Response `{ "ok": true, "hold": "<hold token>" }`.

Vouchers cannot call Events, so "settles it through a lookup" runs through the suite: when the answer is
`VOUCHER_NO_BALANCE` and the voucher has open holds, the error body carries `"lookups": ["<lookup token>", …]` (at
most five). The suite passes each to Events (§8.3), passes every `settle` token Events answers to §8.2, and asks for
the hold again. A booking that already holds the voucher, within that hold's `exp`, gets its hold token back
instead of a second hold.

### 8.2 `POST public/redeem/settle` (Vouchers)

Request `{ "settle": "<settle token>" }`. Verifies it (type `settle`), matches `rid` and `ref` to a hold it issued
(else `REF_UNKNOWN`) and applies §5.2. Response `{ "ok": true, "state": "held" | "confirmed" | "released" |
"credited" }`.

### 8.3 Lookup (Events Pro)

Request `{ "request": "<lookup token>" }`. Events verifies it (type `lookup`) and answers for the booking `ref`:

- the booking carries `rid` and has reached an outcome → `{ "ok": true, "state": "settled", "settle": "<token>" }`;
- the booking carries `rid` and is still open → `{ "ok": true, "state": "pending", "settle": null }`;
- the booking exists but does not carry `rid` → a `released` settle token, as `"settled"`;
- no such booking → `{ "ok": true, "state": "none", "settle": null }`. Vouchers keeps the hold for staff
  ("Unsettled").

### 8.4 Hold on `public/checkout/continue` (Events Pro)

The continue request takes an optional `"voucherHold": "<hold token>"`. Events verifies it (type `hold`) and
applies §5.1. Any failure, or Vouchers not paired, continues the booking without the voucher and reports the code
(`VOUCHER_UNAVAILABLE` when not paired). Booking without a voucher is always possible.

## 9. Error codes

Token codes keep their `esign-intent/1` meanings; the `VOUCHER_*` codes are route codes for the person redeeming.

| Code | Step | Meaning | HTTP |
| --- | --- | --- | --- |
| `TOKEN_TOO_LARGE` | 1 | Over 1024 characters | 413 |
| `TOKEN_MALFORMED` | 2–3 | Not two canonical base64url segments, or the payload is not a JSON object with a valid `cid` | 400 |
| `CLIENT_UNKNOWN` | 4 | `cid` not paired | 401 |
| `CLIENT_REVOKED` | 4 | `cid` revoked in Vouchers' admin | 403 |
| `TOKEN_INVALID` | 5 | HMAC mismatch: wrong prefix, wrong secret, or tampered | 401 |
| `PAYLOAD_INVALID` | 6 | Wrong `v` or `typ`, or a field breaks its schema | 400 |
| `TOKEN_LIFETIME_EXCEEDED` | 6 | Hold `exp − iat > 1800` | 400 |
| `TOKEN_NOT_YET_VALID` | 7 | Issue time more than 60 s in the future | 401 |
| `TOKEN_EXPIRED` | 7 | Past `exp` (hold) or older than 300 s (lookup), plus skew | 401 |
| `PAIRING_MALFORMED` | — | Pairing string fails §3 | 400 |
| `VOUCHER_INVALID` | — | Unknown, expired, void or malformed code: one answer for all | 400 |
| `VOUCHER_NO_BALANCE` | — | Nothing left to spend (spent, or all of it held) | 409 |
| `VOUCHER_WRONG_ACTIVITY` | — | An activity voucher whose ticket type is not in the booking | 409 |
| `VOUCHER_CURRENCY` | — | The voucher's currency is not the booking's | 409 |
| `VOUCHER_UNAVAILABLE` | — | Vouchers not paired or not reachable; book without the voucher | 503 |

`REF_UNKNOWN` (404) and `RATE_LIMITED` (429) are shared route codes. Public routes MAY collapse `CLIENT_UNKNOWN`
and `CLIENT_REVOKED` into `TOKEN_INVALID`.

## 10. Keys, revocation and rotation

As `esign-intent/1` §10, with Vouchers in e-sign's place: revoking a client in Vouchers' admin fails every settle
token under its `cid` with `CLIENT_REVOKED`; Events cannot learn of it, so staff remove or replace the pairing.
To rotate, create a new client, paste its pairing into Events, settle open holds (admin "Unsettled"), then revoke
the old one.

## 11. Versioning

The version is in the prefix (`voucher-hold/1`) and repeated as `v: 1`. Within `/1` only optional fields a `/1`
verifier can ignore may be added; anything else needs `/2` prefixes. The pairing format (`voucher1.`) is versioned
separately.

## 12. Security notes

- The voucher's value moves only in Vouchers' guarded write (§8.1). A hold token can at most discount the one
  booking it names, once; a settle token can at most return what that hold took.
- 80-bit codes, Turnstile on the booking form, a per-IP rate limit on the hold route and one answer for every bad
  code make guessing impractical. Only the SHA-256 of a code is stored.
- Tokens carry no personal data.

## 13. Test vectors

`voucher-vectors.json` has the same shape as `vectors.json` (`esign-intent/1` §13): fixed keys (`keys.A` paired,
`keys.B` another client whose secret is the "wrong secret", `keys.R` revoked), the constants, and a list of
vectors with `type` `hold`, `settle`, `lookup`, `pairing` or `code`. Token vectors have `input.token`,
`verifier { now, clients }` and `expected` `{ ok: true, payload }` or `{ ok: false, error }`.

Code vectors have `input.text` (what was typed) and `expected` `{ ok: true, code, display, id }` or
`{ ok: false }`; generation vectors have `input.bytes` (10 bytes, hex) and `expected.code`.

A conforming implementation MUST produce `expected` for every vector. The file is regenerated with
`node docs/protocol/generate-voucher-vectors.mjs` and must not be edited by hand.

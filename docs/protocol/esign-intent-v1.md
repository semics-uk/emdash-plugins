# esign-intent/1: the Events ↔ E-sign integration protocol

Status: **draft for 1.0** · Version: `esign-intent/1` · Requirements: SX-NFR-01..06 · Source: BUILD-PLAN §5,
§3.1 (waivers), §3.2 (e-sign public routes), decisions R4, R5, R10.

Test vectors: [`vectors.json`](vectors.json), generated by [`generate-vectors.mjs`](generate-vectors.mjs) and
checked by [`vectors.test.mjs`](vectors.test.mjs) (`node --test docs/protocol/vectors.test.mjs`).

The key words MUST, MUST NOT, SHOULD, SHOULD NOT and MAY are used as in RFC 2119 / RFC 8174.

## 1. Purpose and roles

`semics-events` and `semics-esign` are sandboxed EmDash plugins. They cannot share storage, so they
exchange small HMAC-signed tokens through the site (in-process route calls and browser redirects).

| Role | Who | Issues | Verifies |
| --- | --- | --- | --- |
| **Client** | `semics-events` (any paired integration) | intent, lookup, catalog tokens | receipt tokens |
| **Signer service** | `semics-esign` | receipt tokens | intent, lookup, catalog tokens |

A client is registered in the e-sign admin, which creates a `clientId` and a shared secret and shows
the **pairing string** exactly once. Both directions use the same secret; the per-type prefixes (§4)
give domain separation.

## 2. Encoding primitives

### 2.1 base64url

`base64url` is RFC 4648 §5 (alphabet `A–Z a–z 0–9 - _`) **without padding**. Decoders MUST reject,
as malformed:

- any character outside that alphabet, including `=`, `+`, `/`, whitespace and non-ASCII characters;
- a length `≡ 1 (mod 4)`;
- non-canonical encodings: the unused low bits of the last character MUST be zero. (A simple check:
  re-encode the decoded bytes and compare with the input.)

Canonical decoding makes every token have exactly one valid spelling.

### 2.2 Text and JSON

- Payloads are UTF-8 JSON (RFC 8259) whose top-level value is an object. Decoders MUST decode UTF-8
  strictly (invalid sequences are an error, not replaced) and MUST reject a byte-order mark.
- Issuers SHOULD serialise as `JSON.stringify` does: no insignificant whitespace, fields in the order
  the schemas in §5 list them, then any extension fields. The vectors use this form, so an issuer can
  test its output byte for byte.
- Issuers MUST NOT emit duplicate member names. Verifiers MAY reject them; behaviour with duplicates
  is otherwise undefined.
- **No canonicalisation is needed or allowed on verify.** The signature covers the exact
  `payloadB64` characters as received. Verifiers MUST compute the HMAC over the received segment and
  MUST NOT re-serialise the parsed payload.
- All times are integer Unix seconds (UTC) represented as JSON numbers with no fraction or exponent
  part that changes the value: the parsed value MUST be a safe integer `0 ≤ t ≤ 2^53 − 1`.
- Lengths of text fields are counted in Unicode code points. Text fields MUST be well-formed Unicode
  (no lone surrogates from `\uD800`-style escapes).

## 3. Pairing string

```
pairing  = "esign1." clientId "." secret
clientId = 4*64( ALPHA / DIGIT / "-" / "_" )
secret   = 43( base64url character )    ; canonical encoding of exactly 32 bytes
```

- Regex: `^esign1\.([A-Za-z0-9_-]{4,64})\.([A-Za-z0-9_-]{43})$`, plus the canonical-decoding rule
  of §2.1. Anything else is `PAIRING_MALFORMED`.
- The secret is 32 bytes from a CSPRNG. It is the raw HMAC key (no key derivation).
- e-sign SHOULD generate client ids as `cl_` followed by 16 random lowercase base32 characters. Client
  ids are never reused, even after revocation.
- Parsers MUST NOT trim or otherwise normalise the string. Settings UIs SHOULD trim surrounding
  whitespace before saving, because pairing strings are pasted.
- The pairing string is a secret: store it as a `secret` setting, never log it, and show it only at
  creation. `esign1` versions the pairing format, independently of token versions.

## 4. Token format

```
token      = payloadB64 "." signature
payloadB64 = base64url( UTF-8 JSON payload )            ; non-empty
signature  = base64url( HMAC-SHA256( secret, prefix "." payloadB64 ) )   ; exactly 43 characters
```

The HMAC input is the ASCII bytes of the prefix, a `.` and the payload segment exactly as it appears
in the token.

| Token type | Prefix | Issuer → verifier | Max length (characters) |
| --- | --- | --- | --- |
| SigningIntent | `esign-intent/1` | Events → e-sign | 8192 |
| SignedReceipt | `esign-receipt/1` | e-sign → Events | 2048 |
| Receipt lookup request | `esign-lookup/1` | Events → e-sign | 1024 |
| Template catalogue request | `esign-catalog/1` | Events → e-sign | 1024 |

A verifier always knows which type it expects (from the route it serves) and uses only that type's
prefix. Because the prefix is inside the MAC, a token of one type can never verify as another, even
if a `typ` check were missed (R10). There is no header segment and no algorithm negotiation.

The signature MUST be compared in constant time (for example with `crypto.subtle.verify`).

Max length is the token's length in characters. A conforming token is ASCII, so this equals its
byte length. (For a non-ASCII string a verifier MAY report `TOKEN_TOO_LARGE` or `TOKEN_MALFORMED`;
both are rejections, and the vectors only use ASCII.)

## 5. Payload schemas

Every payload starts with these fields:

| Field | Type | Rule |
| --- | --- | --- |
| `v` | integer | MUST be `1` (the version in the prefix) |
| `typ` | string | MUST be `"intent"`, `"receipt"`, `"lookup"` or `"catalog"`, matching the prefix |
| `cid` | string | `clientId` grammar (§3). Selects the key |

Grammars used below:

- `id64` = `^[A-Za-z0-9_-]{1,64}$`
- `ref` = `^[A-Za-z0-9._:-]{1,128}$`, opaque to e-sign. Events uses `<bookingRef>:<attendeeCode>` for
  per-attendee waivers (`signature.mode = "each_attendee"`) and `<bookingRef>` for `mode = "buyer"`.
- `hex256` = `^[0-9a-f]{64}$` (lowercase)
- `name` = 1–200 code points, no C0 control characters or U+007F
- `email` = 1–254 code points, exactly one `@`, a non-empty part on each side, and no code point
  ≤ U+0020 or equal to U+007F

Unknown top-level fields MUST be ignored (they are still covered by the signature). Unknown fields
inside `signer`, `participant` or other nested objects MUST also be ignored.

### 5.1 SigningIntent (`esign-intent/1`)

Issued by Events for one signature, redeemed by e-sign at `public/envelopes/from-intent`.

| Field | Req. | Type | Rule |
| --- | --- | --- | --- |
| `v`, `typ`, `cid` | yes | | `typ: "intent"` |
| `iat` | yes | integer | Issue time |
| `exp` | yes | integer | `exp > iat` (else `PAYLOAD_INVALID`); `exp − iat ≤ 1800` (else `TOKEN_LIFETIME_EXCEEDED`) |
| `nonce` | yes | string | `^[A-Za-z0-9_-]{16,64}$`, at least 96 bits from a CSPRNG (16 random bytes → 22 characters) |
| `tpl` | yes | string | `id64`: template id |
| `tplVersion` | no | integer | ≥ 1. Absent: the template's current published version |
| `ref` | yes | string | `ref` grammar |
| `signer` | yes | object | `{ name: name, email: email }`: the person who signs |
| `as` | no | string | `"self"` (default), `"guardian"` or `"buyer"`: the capacity in which `signer` signs |
| `participant` | iff `as = "guardian"` | object | `{ name: name }`: the minor the guardian signs for. MUST be absent otherwise |
| `delivery` | no | string | `"inline"` (default): the signer is present and signs now. `"email"`: e-sign emails the signer a signing link |
| `prefill` | yes | object | ≤ 32 members; keys `^[A-Za-z0-9_]{1,64}$`; values strings of ≤ 500 code points. May be `{}` |
| `returnUrl` | yes | string | ≤ 2048 characters (else `PAYLOAD_INVALID`); then the rules in §7 |

**Issuer rules (Events, R5).** These are Events obligations; e-sign cannot check them.

- `exp ≤ min(iat + 1800, booking.holdExpiresAt)`: the intent's lifetime is capped at 30 minutes and
  at the booking's remaining hold.
- Waiver mode `each_attendee`: one intent per attendee, `ref = <bookingRef>:<attendeeCode>`. The buyer
  signs inline for themselves (`as: "self"`) and for each attendee marked under 18
  (`as: "guardian"`, `participant` = the minor). Every other adult attendee gets `as: "self"`,
  `delivery: "email"`, with `signer` = that attendee. Events MUST NOT issue an intent in which one
  adult signs for another adult.
- Waiver mode `buyer`: one intent, `ref = <bookingRef>`, `as: "buyer"`, `signer` = the buyer.
- A fresh nonce per intent. To retry a failed call, mint a new intent; idempotency on `(cid, ref)`
  (§8.1) returns the same envelope.

`exp` bounds only when the intent can be redeemed. The envelope it creates has its own expiry
(e-sign setting), which for `delivery: "email"` is usually days.

### 5.2 SignedReceipt (`esign-receipt/1`)

Issued by e-sign when an envelope reaches a terminal status, delivered via `returnUrl#receipt=` and
via `public/receipts/lookup`.

| Field | Req. | Type | Rule |
| --- | --- | --- | --- |
| `v`, `typ`, `cid` | yes | | `typ: "receipt"`; `cid` is the client that created the envelope |
| `envelopeId` | yes | string | `id64` |
| `ref` | yes | string | The intent's `ref` |
| `status` | yes | string | `"completed"`, `"declined"`, `"voided"` or `"expired"` |
| `docSha256` | yes | string | `hex256`: SHA-256 of the document snapshot that was presented |
| `pdfSha256` | yes | string or null | `hex256` or `null` when `status = "completed"` (null while the signed PDF is still being generated); MUST be `null` otherwise |
| `finalHash` | yes | string or null | `hex256` when `status = "completed"`; MUST be `null` otherwise |
| `at` | yes | integer | When the envelope entered `status` |

Receipts carry no `exp`: they are durable evidence, and a signer who completes by email may be
reconciled days later. Replaying a receipt is harmless because processing is idempotent and
monotonic (§8.4). e-sign SHOULD mint receipts deterministically (fixed field order, values taken from
the stored envelope), so the same envelope state always yields the same token.

### 5.3 Receipt lookup request (`esign-lookup/1`)

| Field | Req. | Type | Rule |
| --- | --- | --- | --- |
| `v`, `typ`, `cid` | yes | | `typ: "lookup"` |
| `ts` | yes | integer | Issue time |
| `ref` | yes | string | `ref` grammar |

### 5.4 Template catalogue request (`esign-catalog/1`)

| Field | Req. | Type | Rule |
| --- | --- | --- | --- |
| `v`, `typ`, `cid` | yes | | `typ: "catalog"` |
| `ts` | yes | integer | Issue time |

Lookup and catalogue requests are short-lived and carry no nonce. Both are read-only and idempotent,
and they are sent server-to-server in-process, so replay within the 6-minute window gains nothing.

## 6. Verification

### 6.1 Parameters

| Name | Value |
| --- | --- |
| Clock-skew allowance `S` | 60 s |
| Intent max lifetime | 1800 s (`exp − iat`) |
| Request max age `A` (lookup, catalog) | 300 s |
| Nonce retention | at least until `exp + S`; MAY be longer |

### 6.2 Algorithm

A verifier has: the expected type `T` (and so the prefix), its clock `now`, a client table
`cid → { secret, revoked, returnUrlAllowlist }`, and (for intents) the set of consumed `(cid, nonce)`
pairs. Events, verifying receipts, has a one-entry table built from its pairing string.

Steps run **in this order**, and the first failure is the result. The order is normative so every
implementation reports the same code for a token with several faults.

1. **Size.** Token longer than the max for `T` → `TOKEN_TOO_LARGE`. Nothing is decoded first.
2. **Structure.** Split on `.`: exactly two segments, the payload segment non-empty, both valid
   canonical base64url (§2.1), the signature exactly 43 characters. Else → `TOKEN_MALFORMED`.
3. **Payload decoding.** Decode the payload segment, strict UTF-8, JSON, top-level object, `cid`
   present and matching the `clientId` grammar. Else → `TOKEN_MALFORMED`. *Until step 5 passes,
   nothing in the payload is trusted; `cid` is read only to select a key.*
4. **Client.** `cid` not in the table → `CLIENT_UNKNOWN`. Revoked → `CLIENT_REVOKED`.
5. **Signature.** `HMAC-SHA256(secret, prefix(T) + "." + payloadB64)` compared in constant time with
   the decoded signature. Mismatch → `TOKEN_INVALID`. Wrong prefix, wrong secret, tampered payload
   and tampered signature are indistinguishable here, by design.
6. **Schema.** `v`, `typ` (MUST equal `T`) and the type's fields (§5) → `PAYLOAD_INVALID`.
   For intents, `exp − iat > 1800` → `TOKEN_LIFETIME_EXCEEDED` (after the other schema checks).
7. **Time.**
   - Not yet valid → `TOKEN_NOT_YET_VALID` when `iat` (intent), `at` (receipt) or `ts` (lookup,
     catalog) is greater than `now + S`.
   - Expired → `TOKEN_EXPIRED` when, for an intent, `now > exp + S`; for lookup and catalog,
     `now > ts + A + S`. Receipts do not expire.
8. **Return URL** (intents only). Not allowed by §7 → `RETURN_URL_NOT_ALLOWED`.
9. **Nonce** (intents only). `(cid, nonce)` already consumed → `TOKEN_REPLAYED`. Otherwise record it
   atomically (for example, put-if-absent on a document whose id is `<cid>:<nonce>`, with
   `expiresAt = exp + S`). A lost race also yields `TOKEN_REPLAYED`. The nonce is consumed only when
   every earlier step passed, so a rejected intent never burns a nonce.

On success the result is the decoded payload (with defaults for `as` and `delivery` applied by the
consumer, not written back into the token).

The boundaries are inclusive: `now = exp + 60` is valid, `now = exp + 61` is expired; `iat = now + 60`
is valid, `iat = now + 61` is not yet valid.

### 6.3 Result shape

Verifier libraries return `{ ok: true, payload }` or `{ ok: false, code }` where `code` is one of the
§9 codes. The vectors use exactly this outcome model.

## 7. Return URL allowlist

Each client has an allowlist of entries. An entry is an absolute URL with scheme `https` (or `http`
only for host `localhost`, `127.0.0.1` or `[::1]`), no userinfo, no query and no fragment. Its path
defaults to `/`. If a client has no explicit allowlist, it is `[ <origin of the e-sign site> + "/" ]`
(same-origin by default).

A `returnUrl` is allowed when all of these hold, after parsing both it and the entry with the WHATWG
URL parser (which lowercases the host, removes the scheme's default port and resolves `.`/`..`
segments, including `%2e` forms):

1. It parses as an absolute URL with scheme `https:` or `http:` (relative URLs, `javascript:`,
   `data:` and others are rejected).
2. It has no username or password, and no fragment (not even an empty `#`); the fragment is reserved
   for the receipt.
3. Some entry has the same scheme, the same host, and the same port (both normalised).
4. And for that entry, the path matches by segment prefix:
   - entry path ends in `/`: the URL's path starts with the entry path;
   - otherwise: the URL's path equals the entry path, or starts with the entry path followed by `/`.

   Paths are compared as serialised by the parser, case-sensitively. `https://events.example/booking`
   allows `/booking` and `/booking/BK7Q2M` but not `/bookings`.

The query string is not compared, and is preserved on redirect. Any failure in 1–4 →
`RETURN_URL_NOT_ALLOWED`.

## 8. Endpoints and behaviour

Tokens travel only in JSON POST bodies (`Content-Type: application/json`) or in the URL fragment of
the receipt redirect. They MUST NOT appear in query strings or paths, MUST NOT be logged, and pages
that read them MUST send `Referrer-Policy: no-referrer` (R10). Error bodies carry the §9 code:
`{ "ok": false, "error": { "code": "TOKEN_EXPIRED", "message": "…" } }`; `message` is for humans and
is not stable.

### 8.1 `POST public/envelopes/from-intent` (e-sign)

Request `{ "intent": "<token>" }`. Verifies the intent (§6, type `intent`), then checks that the
template (and `tplVersion`, if given) exists, is published and is available to integrations, else
`TEMPLATE_NOT_FOUND` (a route error, not a token error: the nonce is already consumed, so the
client mints a new intent).

Idempotency on `(cid, ref)`: if an envelope for the pair exists and is in progress or `completed`,
it is returned unchanged and the intent's other fields are ignored. If the existing envelope is
`declined`, `voided` or `expired`, a new envelope is created, so a signer can try again.

Response `{ "ok": true, "envelopeId", "status", "signingToken"? }`. `signingToken` is present only
for `delivery: "inline"` while the envelope awaits this signer; the caller renders the ceremony
in-process with it (`<SigningCeremony token>`). For `delivery: "email"`, e-sign emails the signer.

### 8.2 Receipt redirect

When the ceremony ends (any terminal status), e-sign redirects the browser to
`returnUrl + "#receipt=" + receiptToken`. The token needs no percent-encoding. The UI kit page reads
`location.hash`, removes it with `history.replaceState`, and POSTs the token to Events
`signatures/receipt`. Fragments are not sent to servers or in `Referer` headers.

If the PDF is not ready yet, e-sign MAY redirect with `pdfSha256: null` (§5.2) and issue the full
receipt later through lookup.

### 8.3 `POST public/receipts/lookup` (e-sign)

Request `{ "request": "<lookup token>" }`. Verifies it (type `lookup`), then finds the most recent
envelope for `(cid, ref)`, only ever among envelopes created by that `cid`. Response
`{ "ok": true, "state": "terminal", "receipt": "<receipt token>" }`, `{ "ok": true, "state": "pending",
"receipt": null }` (in progress) or `{ "ok": true, "state": "none", "receipt": null }` (no envelope).

### 8.4 `POST signatures/receipt` (Events)

Request `{ "receipt": "<token>" }`. Verifies it (type `receipt`) with the pairing's secret, then:

- matches `ref` to the booking (and attendee) and rejects a `ref` it never issued;
- stores `envelopeId`, `status`, `docSha256`, `pdfSha256`, `finalHash`, and advances the booking state
  machine (§3.1);
- is idempotent: the same receipt twice is a no-op;
- is monotonic: a `completed` receipt is final and is never replaced by a non-completed one for the
  same `ref`. A completed receipt with a non-null `pdfSha256` supersedes one for the same
  `envelopeId` with `pdfSha256: null` (all other fields equal). Among non-completed receipts, a later
  `at` wins.

### 8.5 `POST public/templates/catalog` (e-sign)

Request `{ "request": "<catalog token>" }`. Response
`{ "ok": true, "templates": [ { "id", "name", "version" } ] }` listing only templates flagged
"available to integrations". Events caches it in KV after a manual "Refresh templates".

## 9. Error codes

Stable strings. New codes may be added within `/1`; existing ones never change meaning.

| Code | Step | Meaning | HTTP |
| --- | --- | --- | --- |
| `TOKEN_TOO_LARGE` | 1 | Over the type's max length | 413 |
| `TOKEN_MALFORMED` | 2–3 | Not two canonical base64url segments, signature not 32 bytes, payload not a UTF-8 JSON object, or no valid `cid` | 400 |
| `CLIENT_UNKNOWN` | 4 | `cid` not registered (Events: not its paired client) | 401 |
| `CLIENT_REVOKED` | 4 | `cid` revoked | 403 |
| `TOKEN_INVALID` | 5 | HMAC mismatch: wrong prefix/type, wrong secret, or tampered | 401 |
| `PAYLOAD_INVALID` | 6 | Wrong `v` or `typ`, or a field breaks its schema | 400 |
| `TOKEN_LIFETIME_EXCEEDED` | 6 | Intent `exp − iat > 1800` | 400 |
| `TOKEN_NOT_YET_VALID` | 7 | Issue time more than 60 s in the future | 401 |
| `TOKEN_EXPIRED` | 7 | Past `exp` (intent) or older than 300 s (lookup, catalog), plus skew | 401 |
| `RETURN_URL_NOT_ALLOWED` | 8 | `returnUrl` fails §7 | 400 |
| `TOKEN_REPLAYED` | 9 | Intent nonce already consumed | 409 |
| `PAIRING_MALFORMED` | — | Pairing string fails §3 (settings validation) | 400 |

Route-level codes outside token verification: `TEMPLATE_NOT_FOUND` (404), `REF_UNKNOWN` (Events
receipt for a `ref` it never issued, 404), `RATE_LIMITED` (429).

Public routes MAY collapse `CLIENT_UNKNOWN` and `CLIENT_REVOKED` into `TOKEN_INVALID` in responses to
avoid revealing which client ids exist, but MUST log the precise code.

## 10. Keys, revocation and rotation

- **Revocation** (e-sign admin): sets `revokedAt`. From then on every intent, lookup and catalog token
  for that `cid` fails with `CLIENT_REVOKED`, including tokens issued before revocation. Receipts
  already stored by Events remain valid evidence. Events cannot learn of a revocation; the operator
  removes or replaces the pairing.
- **Rotation**: create a new client, paste the new pairing into Events, and revoke the old client once
  envelopes created under it have reached a terminal status (envelopes are scoped to the `cid` that
  created them, so lookups under the new `cid` do not see them).
- A secret that may have leaked MUST be revoked immediately, accepting that pending envelopes under it
  are reconciled manually.

## 11. Versioning

- The version lives in the prefix (`esign-intent/1`) and is repeated as `v: 1`. A verifier selects
  the prefix from the route it serves, never from the payload.
- Within `/1`, only additive optional fields that a `/1` verifier can safely ignore may be added.
  Anything that changes verification, security semantics, or the meaning of an existing field
  requires `/2`.
- `/2` uses new prefixes (`esign-intent/2`, `esign-receipt/2`, …) and `v: 2`. A `/2` route that must
  accept `/1` during migration verifies with the `/1` prefix explicitly and applies `/1` rules. A `/1`
  token never verifies under a `/2` prefix, and vice versa.
- The pairing format is versioned separately (`esign1.`); it changes only if the key format changes.
- Removing `/1` support is a breaking change of the plugin's trust contract (major version).

## 12. Security notes

- Distinct prefixes prevent cross-type confusion; distinct per-client secrets prevent cross-client
  forgery; `(cid, ref)` idempotency plus single-use nonces prevent duplicate envelopes and intent
  replay.
- The 30-minute intent cap and the hold cap keep a leaked intent's useful life short. The browser
  never sees an intent: Events mints it and redeems it in-process.
- `docSha256`, `pdfSha256` and `finalHash` in the receipt bind the booking to the exact document and
  audit chain, so Events can show and later prove what was signed.
- No PII beyond `signer`, `participant` and `prefill` is carried. Receipts carry no PII.

## 13. Test vectors

`vectors.json` holds fixed keys (`keys.A` paired, `keys.B` another client whose secret serves as the
"wrong secret", `keys.R` revoked) and a list of vectors:

```jsonc
{
  "name": "intent/expired",          // "<type>/<case>", unique
  "type": "intent",                  // intent | receipt | lookup | catalog | pairing
  "description": "…",
  "input": {
    "token": "…",                    // exactly what the verifier receives
    "expectedPrefix": "esign-intent/1",
    "signedWithPrefix": "esign-intent/1",   // how it was minted (absent for unsigned garbage)
    "signedWithSecret": "…",
    "payload": { … },                // the payload that was signed, for reference
    "tamper": "…"                    // present when the token was altered after signing
  },
  "verifier": { "now": 1800000000, "clients": { "<cid>": { "secret", "revoked", "returnUrlAllowlist"? } }, "usedNonces": [ { "cid", "nonce" } ] },
  "expected": { "ok": true, "payload": { … } }   // or { "ok": false, "error": "TOKEN_EXPIRED" }
}
```

Pairing vectors have `input.pairing` and `expected` `{ ok: true, clientId, secret }` or
`{ ok: false, error: "PAIRING_MALFORMED" }`.

A conforming verifier MUST produce `expected` for every vector. A conforming issuer, given
`input.payload`, `signedWithSecret` and `signedWithPrefix` of a vector without `tamper`, SHOULD
produce `input.token` byte for byte. The file is regenerated with
`node docs/protocol/generate-vectors.mjs` and must not be edited by hand.
